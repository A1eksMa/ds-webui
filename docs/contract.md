# Файловый контракт `ds` → `ds-webui`

Единственная связь между проектами. `ds-webui` полагается только на формат ниже, никогда —
на схему БД `ds`.

**Кто что производит.** `ds get --preset <preset.json> --out <dir>` (ядро `ds`) отдаёт по
одному **голому JSON** на источник. Обёртку в `.js` (`window.DS.sources[...] = <json>;`) и
`manifest.js` строит **поллер** — ядро про браузер не знает. Референсная реализация этого
шага и живой пример — [`../tools/gen_sample.py`](../tools/gen_sample.py) → [`../sample-data/`](../sample-data/).

Файлы кладутся в `data/` рядом с `index.html`. Каждый — валидный JS, дописывающий в глобал;
порядок загрузки не важен; повторная загрузка перезаписывает слот источника.

## `data/manifest.js`

Маленький, читается страницей всегда — чтобы показать доступные источники и их колонки
**без загрузки самих данных**.

```js
window.DS_MANIFEST = {
  generated_at: 1706750000.0,        // когда перестроен манифест (unix, сек)
  db_max_cnt: 21,                    // глобальный максимум cnt в БД на момент сборки (информационно)
  sources: [
    {
      name: "CRM",
      file: "CRM.js",
      key: "customer_id",            // ключевой показатель (по нему LEFT JOIN внутри источника)
      description: "CRM, выгрузка из 1С раз в сутки",  // см. ниже; null, если не задано
      as_of: 1706745600.0,           // дата среза, на которую свёрнуто состояние
      generated_at: 1706750000.0,    // когда сгенерирован этот файл источника
      gen_max_cnt: 13,               // cnt, до которого учтены данные в файле (из meta.gen_max_cnt)
      db_max_cnt: 21,                // ТЕКУЩИЙ максимум cnt ЭТОГО источника в БД
      rows: 4,
      labels: ["email", "phone", "status"],  // колонки в файле (выбранные пресетом + вынужденные)
      label_types: { "email": "text", "phone": "text", "status": "text" }  // см. ниже
    }
  ]
};
```

**Детект устаревания:** `db_max_cnt > gen_max_cnt` у источника → файл отстаёт от БД, показать
бейдж «пересобрать». Сравнение **пер-источниковое** — глобальный `db_max_cnt` для этого не
годится (новые транзакции ERP не делают CRM устаревшим).

**`label_types`** (аддитивное поле, с `ds-loader` 0.5.0a1) — `{имя показателя: type}` для
каждого показателя из `labels` (`type` ∈ `"text" | "number" | "date" | "bool"`, как в
`source.json`'s `labels[].type`, см. [`ds/docs/reference/config-format.md`](https://github.com/A1eksMa/ds/blob/main/docs/reference/config-format.md);
показатель без объявленного типа → `"text"`). `ds-webui` использует его как **дефолтный тип
нового индикатора** при создании из сырого поля («+ индикатор», «+ показатель источника» на
«Индикаторах», и неявные индикаторы при пустом пресете) — пользователю не нужно вручную
выставлять «число»/«дата» на каждый показатель, если источник уже объявил тип в
`source.json`. Показатель отсутствует в `label_types` (манифест ещё не содержит поля —
старый поллер, или источник ещё не опубликовал ни одного типизированного показателя) →
дефолт `"text"`, как и раньше. Поле не влияет на уже созданные/сохранённые индикаторы —
только на дефолт в момент создания.

**`description`** (аддитивное поле, с `ds-loader` 0.6.0a1) — верхнеуровневое `source.json`'s
`description`, как есть: что за данные, откуда они берутся. `ds` сам его не использует и не
хранит в БД — справочное поле, источник истины всегда `source.json` (как и
`labels[].type`/`publish`). `null`, если у источника нет `source.json` или в нём нет этого
поля. `ds-webui` показывает его на «Настройках» отдельной строкой **перед** именем
источника — особенно полезно, когда список показателей свёрнут и одно короткое имя
источника малоинформативно.

## `data/<Source>.js`

Ровно то, что отдал `ds get`, обёрнутое в присваивание. `meta` — как в
[`ds/docs/reference/get-output-format.md`](https://github.com/A1eksMa/ds/blob/main/docs/reference/get-output-format.md).

```js
window.DS = window.DS || { sources: {} };
window.DS.sources["CRM"] = {
  "meta": {
    "name": "CRM",
    "key": "customer_id",
    "as_of": 1706745600.0,
    "generated_at": 1706750000.0,
    "gen_max_cnt": 13,
    "include_archive": false,
    "rows": 4,
    "labels": ["email", "phone", "status"]
  },
  "data": [
    { "customer_id": "101", "email": "alice@example.com", "phone": "+7-900-000-0001", "status": "active" },
    { "customer_id": "102", "email": "bob.new@example.com", "phone": "+7-900-000-0002", "status": "vip" },
    { "customer_id": "103", "email": "carol@example.com", "phone": null, "status": "active" },
    { "customer_id": "104", "email": "dave@example.com", "status": "active" }
  ]
};
```

Правила:

- **Широкая таблица:** одна строка на `id`, ключи объекта — `key` источника + выбранные показатели.
- **Значения — строки** (типизация не входит в `ds`, см. его `docs/explanation/data-model.md`).
- **`null`** у ключа = значение удалено в источнике (операция `DELETE`).
- **Отсутствующий ключ** в объекте строки = показателя для этого объекта не было ни в одной
  транзакции. Это не то же самое, что `null`.
- В файл всегда включаются: `key` источника и поля, по которым идёт межисточниковый JOIN
  (даже если пользователь не выбрал их для отображения) — иначе join в браузере не по чему делать.

## Пресет

Продукт «Конструктора выборки». Две секции: `query` понимает `ds get`, `view` — только UI.

```json
{
  "name": "base",
  "description": "CRM + ERP — демо-пример",
  "query": {
    "as_of": null,
    "sources": {
      "CRM": { "labels": ["customer_id", "email", "phone", "status"] },
      "ERP": { "labels": ["price", "stock"] }
    }
  },
  "view": {
    "joins": [
      { "left": "CRM", "left_field": "customer_id", "right": "ERP", "right_field": "client_ref", "type": "left" }
    ],
    "conditions": [
      { "field": "CRM.status", "op": "eq", "value": "active" }
    ],
    "entityConditions": [
      { "field": "Выручка", "op": "gt", "value": "0" }
    ]
  }
}
```

- `name` — имя пресета; уходит в имя файла при скачивании («Скачать пресет» на
  «Настройках» спрашивает оба — имя файла и описание, по умолчанию предлагая в описание
  только что введённое имя файла).
- `description` (опционально, по умолчанию `""`) — человекочитаемый заголовок,
  показывается в шапке страницы (`view-common.js::viewNav`) на всех трёх страницах.
  Отдельно от `name` специально: можно открыть скачанный `.json` текстовым редактором и
  поправить описание, не трогая имя файла. Нулевой пресет (ничего не выбрано) → пустая
  строка в заголовке, не плейсхолдер.
- `query.as_of: null` → `ds get` берёт текущую дату/время. Перекрывается флагом `--dt`.
- `query.sources[].labels` → `ds get --lb …`. **Имя ключевого показателя тут допустимо**:
  `ds get` его молча пропускает (ключ и так есть в каждой строке), а UI трактует его как
  «показывать колонку ключа». То есть ключ — обычное выбираемое поле в списке полей.
- `view.joins` — межисточниковый JOIN (`left.field = right.field`), делается в браузере.
  `type` ∈ `left` (по умолчанию, обратная совместимость со старыми пресетами без этого поля),
  `right`, `inner`, `full` — определяет, какие несовпавшие строки остаются в выборке (с
  `undefined`/пустыми ячейками там, где пары не нашлось): `left` — все строки источника
  `left`, `right` — все строки источника `right`, `inner` — только совпавшие, `full` — все
  строки обеих сторон. Сопоставление — по строковому значению ключа (`Map`), без учёта
  повторов справа: при дублирующемся ключе побеждает последняя строка с этим значением —
  это не полноценный реляционный JOIN с декартовым произведением. `left` в связке может
  называть **любой** источник, уже вошедший в выборку раньше (не обязательно
  непосредственно предыдущий по порядку `query.sources`) — так строится цепочка/дерево
  связок, а не только линейная цепочка.
- `view.conditions` — первый проход фильтрации: список условий `{ field, op, value }`,
  задаётся на странице «Настройки», применяется **сразу после JOIN**, ещё **до** расчёта
  индикаторов. `field` — сырой столбец источника (`Источник.показатель` при нескольких
  источниках). `view.entityConditions` — второй проход, того же формата, задаётся на
  странице «Индикаторы», `field` — имя индикатора из `view.entities`, применяется **после**
  их расчёта; видит и скрытые (`hidden: true`) индикаторы — по ним можно фильтровать, не
  выводя их в таблицу. Оба списка независимы (не путать одно с другим — раньше это была
  единая секция, переключавшаяся на имена сущностей, как только они появлялись; теперь эти
  два уровня разведены). Условие на столбец, которого в выборке нет (устаревший пресет,
  переименованная сущность), **пропускается** — не обнуляет выборку. `op` ∈ `contains`,
  `not_contains`, `eq`, `ne`, `in`, `not_in`, `starts`,
  `ends`, `gt`, `gte`, `lt`, `lte` (числовое сравнение; пустая ячейка не подходит), `empty`,
  `not_empty` (`value` игнорируется). Строковые операторы — без учёта регистра. Для `in` /
  `not_in` `value` — список значений (одно на строку либо через `,` `;` таб); в UI его можно
  вставить из буфера обмена.
  Старое поле `view.column_filters` (`{колонка: подстрока}`) при загрузке пресета
  мигрирует в `conditions` с оператором `contains`.
- `view.entities` — **столбцы таблицы**, формируются из выбранных полей на странице
  «Индикаторы» (отдельная от «Настроек», где выбираются сами источники/поля/связки/условия).
  Это браузерный **Level 2** (см.
  [`ds/docs/explanation/single-source-fold.md`](https://github.com/A1eksMa/ds/blob/main/docs/explanation/single-source-fold.md)):
  разрешение коллизий, типизация, формат. Пусто → каждое выбранное поле = неявная 1:1-сущность
  (`type: "text"`). Порядок массива = порядок столбцов. Одно и то же сырое поле может входить
  в список несколько раз (как есть и/или как вход производной) — не блокируется, коллизия имён
  на выходе разруливается автодобавлением ` (2)`, ` (3)` и т.д. (см. `entityOutNames`).

  ```jsonc
  {
    "name": "Цена",              // алиас = заголовок; дефолт — имя поля
    "type": "number",           // "text" | "number" | "date" | "bool"
    "hidden": false,             // true — считается и виден условиям view.entityConditions,
                                  //   но не выводится в таблицу/экспорт
    "parse": {                   // опц., по type
      "date_in": "auto",        // "auto" (ISO, DD.MM.YYYY, unix-время, серийная
                                //   дата Excel 5–7 цифр) | "excel" (только серийная)
                                //   | токенный шаблон (YYYY MM DD HH mm ss)
      "date_out": "YYYY-MM-DD", // ISO по умолчанию — тогда >/< в фильтрах = хронологические
      "true": "да,true,1",      // bool: токены истины (csv, регистронезависимо)
      "decimal": "auto"         // number: "auto" | "." | ","
    },
    "format": { "width": 140, "align": "right", "font_size": null },
    // ^ в UI больше не настраивается (используются дефолты); значения из
    //   загруженного пресета всё ещё применяются. Ширину столбца задают на
    //   «Таблице» — см. view.column_widths ниже.
    "from": {
      "kind": "field",                                         // одно поле как есть
      "column": "ERP.price",
      // или "kind": "resolve" — разрешение коллизии:
      "inputs": [ { "column": "ERP.price", "weight": 0.9 },
                  { "column": "CRM.price", "weight": 0.4 } ],
      "null_wins": true,        // null (DELETE) из весомого входа побеждает
      // или "kind": "derived" — производная:
      "op": "sum",             // sum|avg|min|max|concat|first_nonempty|count_nonempty
      "sep": " "               // для concat
    }
  }
  ```

  - **Веса `p` задаёт пользователь в интерфейсе** (лежат в пресете). `resolve` берёт вход с
    наибольшим весом среди присутствующих; при **равных весах** — по **порядку входов в
    списке** (пользователь сортирует). Тайбрейк по `dt`/`cnt` (как в модели ядра) **не
    поддержан** — их нет в выгрузке `ds get`; схема оставляет место под будущее
    `{value, dt, cnt}` на ячейку.
  - `type` управляет парсингом строки в значение. Промах парсинга → в таблице **сырой текст с
    подсветкой** (класс `unparsed`), в сортировке такие ячейки — в конце, как пустые.
  - Условия `view.entityConditions` фильтруют **столбцы-сущности** (после резолва), сравнение —
    по отображаемой строке (для дат держи `date_out` в ISO).
- `view.column_widths` — `{ "<столбец>": px }`, ручная ширина столбцов «Таблицы» (тянуть
  правую границу заголовка; двойной клик по границе — сброс). Ключ — имя столбца как в
  таблице (`Источник.показатель` при нескольких источниках). Нет записи → `format.width`
  сущности, иначе дефолт (150 px). Таблица рендерится `table-layout: fixed`.
- **Пресет по умолчанию** — данные, а не код, как и всё остальное в этом контракте:
  `base.js` рядом с манифестом в `data/` или `sample-data/`, тот же способ загрузки
  (инъекция `<script>`), тот же принцип (валидный JS, не JSON — см. выше про `file://`):

  ```js
  window.DS_BASE_PRESET = { name: "base", query: {...}, view: {...} };  // формат — как у пресета выше
  ```

  - `sample-data/base.js` коммитится (генерится [`../tools/gen_sample.py`](../tools/gen_sample.py)
    вместе с остальным `sample-data/`) — есть всегда.
  - `data/base.js` — опционален, кладётся пользователем или поллером рядом со своими
    данными; переживает обновление кода `ds-webui`, как и сам `data/` (не в релизном
    архиве, не в git).
  - Есть `data/`, а `data/base.js` в нём нет → подставляется **пустой** пресет (без
    источников), а не пресет из `sample-data/` — он про поля конкретно CRM/ERP примера,
    которых в чужих данных может не быть.
- Пользовательские пресеты — скачиваются/загружаются файлом через «Конструктор»;
  последний применённый (базовый или загруженный) дополнительно запоминается в
  `localStorage` и на следующей загрузке побеждает пресет по умолчанию.

### Что НЕ входит в пресет

На странице «Таблица» есть ещё несколько слоёв фильтрации/группировки и сортировка —
**транзиентные**, живут только в памяти вкладки, не пишутся в пресет и не сохраняются в
`localStorage`:

1. **Расширенный фильтр** — скрытая по умолчанию область НАД таблицей (кнопка-переключатель
   с пиктограммой-воронкой в навбаре, индикатор ▸/▾; открывается только когда уже есть
   построенная таблица; данные таблицы остаются видны, пока их фильтруешь — не отдельная
   страница), три блока:
   - **«Установить фильтр»** — строки `[И/ИЛИ] · поле · оператор · значение`, те же
     операторы, что в `view.conditions`; можно несколько условий на один столбец. Связка на
     каждой строке: `И` приоритетнее `ИЛИ` (`a И b ИЛИ c` = `(a И b) ИЛИ c`). Применяется
     **после** `view.conditions`. Сбрасывается кнопкой «Показать все» и при пересборке из
     «Конструктора». **Это то же состояние, что быстро дополняет пиктограмма-воронка в
     шапке столбца** (см. ниже) — панель и пиктограмма редактируют один список условий.
   - **«Сгруппировать»** — список полей, применяются **вложенно по порядку** (сначала
     первое, внутри каждой его группы — второе, и т. д.); каждый узел дерева
     сворачивается/разворачивается независимо (кнопки «развернуть все» / «свернуть все» —
     по всем уровням сразу).
   - **«Отсортировать»** — список уровней `поле · направление`, порядок строк = приоритет
     (`ORDER BY поле1, поле2, ...`); числовые значения сравниваются как числа, пустые —
     всегда в конце. **То же состояние, что быстро дополняет пиктограмма-сортировка** в
     шапке столбца (см. ниже) — панель и пиктограмма редактируют один список уровней.
2. **Три пиктограммы под именем каждого столбца** в шапке таблицы — быстрый доступ без
   открытия расширенной панели:
   - **поиск** (лупа) — открывает поле ввода; `Enter` переходит к следующей строке ниже,
     чьё значение в этом столбце содержит введённый текст (с оборотом в начало, если ниже
     совпадений не осталось); если строка внутри свёрнутой группы — группа раскрывается
     по дороге. Не фильтрация, ничего не меняет в выборке. Нет аналога в расширенной панели.
   - **фильтр** (воронка) — открывает поле ввода; `Enter` добавляет/обновляет в **том же
     списке**, что редактирует «Установить фильтр», условие `содержит` на этот столбец
     (`conj: "and"` при добавлении); пустое значение убирает условие.
   - **сортировка** — без поля ввода, сразу переключает этот столбец в **том же списке**,
     что редактирует «Отсортировать»: нет записи → по возрастанию (добавляется в конец
     списка, не трогая уже выставленные уровни) → по убыванию → без сортировки.
   Поле ввода у пиктограмм «поиск» и «фильтр» — один и тот же визуальный компонент
   (включая выпадающий список первых N уникальных значений столбца в порядке строк, с
   настраиваемым N — «Показать N» под списком, `N=0` выключает список), различается
   только то, что делает `Enter`.

Порядок на «Таблице»: `view.conditions` (при построении) → расширенный
фильтр+пиктограмма-фильтр (общий список условий) → сортировка (панель+пиктограмма, общий
список уровней) → группировка.

## Детект устаревания

Страница сравнивает `manifest.db_max_cnt` с `source.gen_max_cnt`: если файл источника отстаёт
от БД — показать бейдж «пересобрать». Перегенерацию делает поллер (по базовому пресету) или
пользователь вручную (`ds get --preset ...`).
